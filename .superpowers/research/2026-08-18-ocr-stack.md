# OCR Stack Feasibility Research — RapidOCR/PP-OCR on onnxruntime-node

Date: 2026-08-18
Scope: Replace server-side tesseract.js OCR with PP-OCR ONNX models running on onnxruntime-node inside a single `node:22-bookworm-slim` container, multi-arch (linux/amd64 + linux/arm64, targeting Synology NAS), zero network egress at runtime, permissive licensing only.

All version numbers/dates below were pulled live from the npm registry, PyPI, GitHub, ModelScope, and Hugging Face on 2026-08-18 — do not trust model training data for these figures on future reads of this file.

## 1. onnxruntime-node

- **Latest stable: 1.27.0** (published 2026-06-19T21:08Z). License: **MIT**.
- **Distribution model is NOT per-platform optional deps** (unlike `sharp`). The single `onnxruntime-node` tarball bundles native binaries for *every* supported platform inside `bin/napi-v6/`:
  - `darwin/arm64` (dylib + `.node`) — 75 MB unpacked
  - `linux/arm64` (`.node` only, no separate dylib) — **20 MB unpacked**
  - `linux/x64` (`.node` only) — **37 MB unpacked**
  - `win32/arm64` (dll + `.node`) — 67 MB
  - `win32/x64` (dll + `.node`) — 62 MB
  - Total unpacked package size: **~259 MB** (`unpackedSize: 270,827,297` bytes from npm registry metadata), because `npm install` pulls all five platform payloads regardless of target OS/arch.
  - **Action item for image size**: add a Docker build step that deletes `node_modules/onnxruntime-node/bin/napi-v6/{darwin,win32}` after `npm ci` — this removes ~204 MB of dead weight per architecture and is safe since we only ever run on linux/amd64 or linux/arm64.
- **linux/arm64 prebuilt binary confirmed present** (`onnxruntime_binding.node`, glibc-linked, not musl) — good, this directly answers "does it ship prebuilt binaries for linux/arm64 (glibc)": **yes**.
- **Node.js version support**: officially "Node.js v16.x+ (recommend v20.x+)". No documented incompatibility with Node 22; no GitHub issues found reporting Node 22-specific breakage.
- **glibc / bookworm-slim compatibort**: Debian 12 (bookworm) ships glibc 2.36, which comfortably exceeds ONNX Runtime's typical build baseline (manylinux2014-class, glibc ~2.28+). No reports found of onnxruntime-node failing to load specifically inside `node:*-bookworm-slim`.
- **Known arm64 risk (see also Q6 below)**: ONNX Runtime's MLAS kernel dispatch has historically assumed all arm64 targets support ARMv8.2 (FP16) and later dot-product/i8mm extensions. Confirmed real issues:
  - [microsoft/onnxruntime#23152](https://github.com/microsoft/onnxruntime/issues/23152) — cross-compiling ORT 1.17.1 for Cortex-A53 fails because A53 lacks ARMv8.2 FP16. **Scoped to custom Yocto cross-compiles**, not the official npm-distributed prebuilt binary.
  - [microsoft/onnxruntime#23957](https://github.com/microsoft/onnxruntime/issues/23957) — Python `onnxruntime` on a stock Raspberry Pi 4 (Cortex-A72, ARMv8.0, no FP16) running Debian Bookworm 64-bit crashes with "Illegal instruction" immediately on import. Root cause/fix not confirmed resolved in the visible thread. This is the **official PyPI wheel**, built by the same ORT release pipeline that produces the Node.js napi binary — so the same class of crash is a plausible (not confirmed) risk for `onnxruntime-node` on comparably old ARM cores.
  - No report found of `onnxruntime-node` itself crashing on Synology hardware specifically — see Q6 for the full risk assessment and why this doesn't necessarily mean "use a sidecar."
- **Approx installed size per platform** (from tarball inspection above): linux/arm64 ≈ 20 MB, linux/x64 ≈ 37 MB (native binary only; add the ~10 MB pure-JS wrapper code shared across platforms).

**Honest verdict**: There is no mature, widely-adopted npm wrapper for PP-OCR-on-`onnxruntime-node`. The one credible candidate (`paddleocr` / paddleocr.js) is well-architected and license-clean but is a low-adoption, single-maintainer project (15 stars) — not something to take a hard runtime dependency on for a production self-hosted app without vendoring/forking it and adding our own test coverage.

**Recommendation: implement the det→crop→rec pipeline ourselves on `onnxruntime-node`, using `paddleocr.js`'s MIT-licensed source as a reference implementation** (and reusing pieces of it directly, with attribution, where they're correct) rather than taking it as a live dependency. Effort estimate for a from-scratch implementation with test fixtures:
- **DBNet detection post-process** (binarize probability map → connected components → polygon approximation → Vatti-clipping box expansion) — the well-known, widely-ported part of PaddleOCR; RapidOCR's own Python source is a clean, readable reference. ~1 day.
- **Crop + perspective/rotate boxes** — trivial with `sharp` (affine/extract + rotate), since boxes from DBNet are usually near-axis-aligned quads for receipts. ~0.5 day.
- **CTC greedy decode** (argmax per timestep, collapse repeats, drop blank token, map indices via the dict file) — a few dozen lines. ~0.5 day.
- **Angle classifier integration** (run cls model, rotate 180° if needed) — optional for receipts since camera capture with edge-detection auto-crop (Q5) should already normalize orientation; can be deferred/dropped initially. ~0.5 day if included.
- **Wiring + onnxruntime-node session management, batching, test fixtures against real receipt images** — 1–2 days.
- **Total: ~3–4 engineer-days** for a working, tested pipeline. This is a bounded, well-precedented task, not an open-ended research problem — multiple public implementations (Python RapidOCR, `paddleocr.js`, `RapidOcrNet` for .NET) all solve exactly this and can be cross-checked against.

## 4. sharp (image preprocessing)

- **Latest: 0.35.3** (published 2026-07-01). License: **Apache-2.0**.
- Ships via **per-platform optional dependencies** (the well-behaved pattern) — `@img/sharp-linux-arm64`, `@img/sharp-linux-x64`, `@img/sharp-libvips-linux-arm64`, `@img/sharp-libvips-linux-x64`, etc. — npm/pnpm/yarn only install the binaries matching the actual install platform, so Docker image size stays lean automatically (unlike `onnxruntime-node`, no manual pruning needed).
- **linux/arm64 prebuilt confirmed** (both `@img/sharp-linux-arm64` for the addon and `@img/sharp-libvips-linux-arm64` for the underlying libvips shared lib) — glibc build, correct for `bookworm-slim` (must ensure the Docker build doesn't accidentally resolve the `linuxmusl` variants, which are Alpine-only; bookworm-slim is glibc-based so this resolves correctly by default via npm's platform detection).
- No open issues or reports suggesting problems on Node 22 / bookworm-slim / arm64 — this is a mature, extremely widely-deployed package (essentially the standard choice for Node image processing) and is low-risk. Confirmed fine to use as-is.

## 5. Browser-side scanner capture (jscanify + opencv.js)

- **jscanify**: latest **1.4.3** (published 2026-07-20 — actively maintained). License: **MIT**. GitHub: 1.8k stars, 81 forks (`puffinsoft/jscanify`, formerly `colonelparrot/jscanify`).
- **Requires OpenCV.js** as a hard dependency (a global `cv` object). The README's own example loads it via **CDN script tag** pointing at `docs.opencv.org/4.7.0/opencv.js` — not acceptable as-is for a LAN-only, zero-egress app, but this is just an example, not a hard requirement to use the official CDN.
- **Self-hosting is viable**: `@techstark/opencv-js` is an actively maintained npm package (Apache-2.0 license) that republishes prebuilt OpenCV.js/WASM builds for direct `npm install` + static-asset serving — no CDN needed. Critically, it publishes a **`4.7.0-release.1`** version that matches the exact OpenCV.js version jscanify was built/tested against, avoiding cross-version API drift (OpenCV.js 5.0.x, also published by the same package, changes enough of the API surface that pairing it with jscanify untested would be risky). **Recommendation: pin `@techstark/opencv-js@4.7.0-release.1`.**
- **Size**: the OpenCV.js WASM binary itself is commonly cited at **~8 MB** (matches independent sources describing it as "large, blocks page load, load async"). The `@techstark/opencv-js` npm package (which bundles multiple version variants across its history) is 14.7 MB unpacked for a single pinned version's install — this is a one-time asset served from our own container with long-lived cache headers, not a per-request cost, and not a network-egress violation once vendored.
- **Mobile browser support**: `getUserMedia` (camera capture) itself is broadly supported on iOS Safari and Android Chrome. **However — critical, project-relevant gotcha found in this research**: `getUserMedia` is gated behind the browser's **secure context** requirement (HTTPS, or `localhost`/`file://`). **A page served over plain `http://<nas-lan-ip>:port` will NOT get camera access in either Safari or Chrome** — `navigator.mediaDevices` is simply `undefined` in that case. Since this app is explicitly LAN-only/self-hosted and likely reached via a bare IP or hostname without a public CA-issued cert, **this is a real deployment blocker for the camera-scan feature specifically**, independent of anything OCR-related. Mitigation options to design around, not skip: (a) terminate TLS in front of the container (reverse proxy with a self-signed/local-CA cert that users install once, or a Synology-issued LAN cert), or (b) issue a real cert via DNS-01 ACME challenge for a home domain even though the service itself stays LAN-only. This needs to be decided before camera capture is built, not discovered at QA time.
- **Alternatives evaluated**:
  - **JSFeat** (`inspirit/jsfeat`) — pure JS, ~23 KB, has Canny/Sobel/Scharr edge-detection primitives, no WASM dependency. **However: effectively unmaintained** (latest npm publish ~10 years ago, v0.0.8) and only provides low-level CV building blocks — no ready-made "find document quadrilateral, warp, crop" pipeline like jscanify has. Using it would mean re-implementing jscanify's contour-detection/quad-approximation/perspective-warp logic from scratch on top of raw primitives — realistically more total engineering effort than the ~8 MB WASM cost of the OpenCV.js route.
  - No other actively maintained, sufficiently-complete, permissively-licensed pure-JS document-scanner library surfaced in this research. The rest of the ecosystem for this exact task (browser document edge-detection + auto-crop) converges either on OpenCV.js-based approaches (jscanify, various tutorials/CodePens) or commercial SDKs (Dynamsoft, Scanbot) — the latter excluded by the "permissive licensing only" / self-hosted constraint.
- **Honest verdict**: **jscanify 1.4.3 + self-hosted `@techstark/opencv-js@4.7.0-release.1`** is the smallest workable *reliable* stack. The ~8 MB WASM payload is a real but one-time, cacheable, non-networked cost — acceptable given no smaller, maintained alternative exists. The secure-context/HTTPS requirement for `getUserMedia` is the bigger practical risk to plan for, not the library choice itself.

## 6. What would force a sidecar instead of in-process onnxruntime-node on arm64

No search result surfaced a genuine architectural reason (licensing, driver isolation, GPU requirement, etc.) that would force a sidecar container. The one real risk found is a **CPU-microarchitecture compatibility risk**, not something a sidecar would fix:

- ONNX Runtime's ARM64 kernels (MLAS) have a history of assuming ARMv8.2 FP16 / later dot-product / i8mm instruction extensions are present on "arm64" as a monolith, when in practice many real-world arm64 SoCs are plain ARMv8.0-A cores without them.
- Confirmed concrete evidence: a stock **Raspberry Pi 4 (Cortex-A72, ARMv8.0, no FP16)** running Debian Bookworm 64-bit crashes with "Illegal instruction" simply importing the official Python `onnxruntime` wheel ([#23957](https://github.com/microsoft/onnxruntime/issues/23957), unresolved in the visible thread). That the affected chip is a *mainstream, fairly modern* core (not some obscure embedded chip) — and the wheel in question is the same official ORT release artifact family that produces `onnxruntime-node`'s native binary — means this class of failure is a **plausible, not merely theoretical, risk** for `onnxruntime-node` on comparably old ARM cores.
- **This directly matters for Synology**: Synology's arm64 NAS lineup spans a wide range of SoCs across product generations — older/budget models (e.g., many units historically shipping Realtek **RTD1296**) use **Cortex-A53** (even older than the Pi 4's A72, definitely lacking FP16/dotprod), while newer budget units (DS223/DS223j-class) use Realtek **RTD1619B**, which is **Cortex-A55** (ARMv8.2-A, does have FP16) — so risk is real but hardware-dependent across the fleet, not a blanket "all Synology arm64 breaks" situation.
- No direct GitHub issue or forum report was found describing `onnxruntime-node` (specifically, not generic Python `onnxruntime`) crashing on a Synology device — this appears to be genuinely unreported territory, not a confirmed-safe or confirmed-broken situation.
- **Why this doesn't argue for a sidecar**: a sidecar container on the same physical NAS would run the exact same arm64 binary against the exact same CPU and would crash identically — containerization doesn't change instruction-set availability. The correct mitigation is (a) **test on real target hardware** (or at minimum an emulated Cortex-A53/A72 profile, e.g. QEMU with `-cpu cortex-a53`) before shipping, and (b) **keep a pure-WASM fallback path** (`onnxruntime-web`'s wasm backend, which runs on V8's portable WASM baseline rather than native SIMD instruction assumptions) that the app can fall back to automatically if the native `onnxruntime-node` binding throws or the process crashes at model-load time on a given box. This is a runtime feature-detection/fallback concern, not a container-topology concern.

## RECOMMENDED STACK

**Server-side OCR (Node process, in-container, no sidecar):**
- `onnxruntime-node@1.27.0` (MIT) — prebuilt linux/arm64 + linux/x64 binaries confirmed present; strip `bin/napi-v6/{darwin,win32}` in the Docker build to cut ~204 MB of unused platform binaries from the image.
- `sharp@0.35.3` (Apache-2.0) — image preprocessing (deskew/normalize/crop), per-platform optional deps already keep this lean; no changes needed.
- **Self-implemented** det→crop→rec pipeline on top of `onnxruntime-node`, written from scratch using RapidOCR's Python source and the MIT-licensed `paddleocr.js` (`x3zvawq/paddleocr.js`) as reference/inspiration rather than as a live dependency (too low-adoption/single-maintainer to depend on directly; ~3-4 engineer-days to implement: DBNet postprocess, sharp-based crop, CTC greedy decode).
- Skip the angle-classifier model initially (orientation should already be normalized by the browser-side scanner crop) — add `ch_ppocr_mobile_v2.0_cls_mobile.onnx` (0.56 MB) later only if real-world receipts show rotation issues.

**Vendored model files (downloaded once at build time from ModelScope, hash-verified against `default_models.yaml`, baked into the image — zero runtime egress):**
- `ch_PP-OCRv5_det_mobile.onnx` — 4.60 MB (detection)
- `en_PP-OCRv5_rec_mobile.onnx` — 7.51 MB (English + digits recognition)
- Recognition dictionary `.txt` extracted from the `rapidocr` PyPI wheel or RapidOCR GitHub source at tag `v3.9.2` (exact bundled path to confirm during implementation)
- Total vendored payload: **~12–13 MB** — negligible image-size impact.
- License: Apache-2.0 throughout (RapidOCR conversion + underlying PaddleOCR weights, confirmed via PaddleOCR's LICENSE and the Hugging Face `PaddlePaddle/PP-OCRv5_mobile_det` model card's explicit `apache-2.0` tag) — compatible with the MIT/Apache-2.0/BSD-only constraint.

**Browser-side scanner capture:**
- `jscanify@1.4.3` (MIT) + self-hosted `@techstark/opencv-js@4.7.0-release.1` (Apache-2.0, version-pinned to match jscanify's tested OpenCV.js API) served as a static asset from the same container — no CDN, satisfies zero-egress.
- **Must resolve HTTPS/secure-context for the LAN deployment before this feature can work at all** — `getUserMedia` is blocked on plain HTTP even for LAN IPs on both Safari and Chrome. Decide the TLS approach (reverse-proxy self-signed cert, local CA, or DNS-01 ACME cert for a LAN-facing hostname) as part of this feature's design, not as a bug found later.

**Fallback plan (risk mitigation, not a sidecar):**
- Treat older/budget-tier arm64 Synology units (Cortex-A53-class, e.g. RTD1296-based models) as a real compatibility risk for `onnxruntime-node`'s native arm64 binary, based on documented "illegal instruction" crashes affecting even the newer Cortex-A72 on official ORT wheels. Before shipping: smoke-test the actual container on real target hardware (or QEMU with an explicit older-core CPU profile).
- If the native binding fails to load or crashes at startup on a given box, fall back at runtime to `onnxruntime-web`'s WASM execution provider (portable, no native ISA assumptions) rather than standing up a sidecar — a sidecar on the same host CPU would hit the identical instruction-set incompatibility.
- Keep the current tesseract.js path available behind a feature flag for at least one release as an absolute last-resort fallback for hardware where neither ORT path works, given tesseract.js's WASM-only execution has no comparable native-ISA risk.
